# 查詢、修改、取消報名只能經過網站伺服器

查詢、修改、取消報名的資料庫函式（`lookup_registration`、`update_registration`、`cancel_registration`）只開放給網站伺服器，訪客不能拿公開的 publishable key 直接呼叫。網站伺服器用放在 Vercel 環境變數的 `SUPABASE_SECRET_KEY` 呼叫，而且只用固定的方式呼叫。送出報名不比對身分，仍開放給訪客直接呼叫。

ADR 0002 用「同一個姓名猜錯 10 次就暫停」擋住一組一組猜電話或報名編號，猜錯的紀錄和比對在同一個交易裡寫入。訪客能直接呼叫時，可以要 PostgREST 對回傳值同時加篩選與轉型（例如 `?pgrst_scalar=eq.[]&select=pgrst_scalar::boolean`）：猜錯的回傳值通過篩選、轉型失敗，整個交易撤銷，猜錯紀錄跟著不見；猜對的被篩掉、正常回應。這樣不必知道報名 id，就能不計次數猜到某個姓名的電話，看到她的個資。改回傳值的形狀擋不住這種組合，所以從入口擋。

## Considered Options

- 回傳值不透露猜對與否，結果另外再取（先寫進一張表，再用另一次呼叫讀）：不必設定秘密金鑰，但每個動作都變成兩步，程式難懂，交接成本高。
- 猜錯紀錄不跟著交易撤銷（例如用 dblink 另開連線寫入）：依賴額外的擴充功能，出錯時難查。

## Consequences

- Vercel 多一個秘密環境變數 `SUPABASE_SECRET_KEY`（名稱不能加 `NEXT_PUBLIC_`，否則會送到瀏覽器）。Supabase 換 key 時要一起更新；沒設定或設錯時，查詢、修改、取消都會失敗。
- `src/lib/supabase/service.ts` 是唯一用秘密金鑰的地方，標了 `server-only`，被瀏覽器端的程式引用時建置會失敗。秘密金鑰略過資料表權限，所以只拿來呼叫這三個函式。
- 資料庫函式仍保留之前的防護（唯讀呼叫一律拒絕、比對不到回傳 `{}`、身分對上之後錯誤放在回傳值不丟例外），萬一權限設錯，也比較難被利用。
- 正式環境更新時，資料庫先推、網站後部署，中間幾分鐘查詢與修改會失敗（舊網站還在用 publishable key）。
